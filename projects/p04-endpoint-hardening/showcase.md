## The problem

Halden's PCs were set up by whoever unboxed them. Every user is a local administrator, BitLocker is
off, Defender runs on its defaults only, and about 30% of devices still run Windows 10, which lost
support on 14 October 2025. The business therefore cannot answer three ordinary questions: is a lost
sales laptop a data breach, is ransomware behaviour actually blocked, and what will moving off Windows
10 cost? Industry data puts about **21% of small-business Windows devices still on Windows 10 in
mid-2026** (Lansweeper, via Computer Weekly), and Microsoft's commercial Extended Security Updates run
for at most three years and are paid for annually — so waiting has a price as well as a risk.

## What I built

- **A measured "before" state** — BitLocker status, local Administrators membership, Defender
  configuration, ASR mode and a CIS/Microsoft baseline score — captured by one script and repeated the
  same way afterwards, so any before/after claim has two real files behind it.
- **The Microsoft Security Baseline imported through Group Policy** into a new GPO, with a separate
  higher-precedence overrides GPO for documented deviations and a Policy Analyzer comparison against
  the existing P1–P3 GPOs before anything reached the fleet.
- **Sixteen Defender Attack Surface Reduction rules, audit first and block second.** The seven-day audit
  period is enforced in code, and only registered exceptions survive the move to blocking.
- **BitLocker (XTS-AES 256, TPM-only startup) with recovery keys escrowed to Active Directory** — and a
  script that refuses to encrypt until the escrow policy is confirmed, plus a tested helpdesk recovery
  runbook with an identity-verification step.
- **Local administrator rights removed**, with a published software-request process and time-limited
  elevation: the answer to "I need admin for one app" is a process, not a permanent exception.
- **Firewall, Credential Guard, LSA protection and PowerShell logging** applied consistently, with the
  remote-management rules designed here and narrowed to the management subnet in P6.
- **A daily compliance report over nine named controls**, producing an HTML traffic-light report and a
  CSV for management reporting — where a check that cannot run is shown as amber and excluded, never
  counted as a pass.
- **A Windows 11 readiness assessment** that runs the same classification rules over the lab's real
  machines and over a clearly labelled **synthetic** fleet, with a costed three-option recommendation.

## How it works

![P4 endpoint hardening architecture](./evidence/public/p04-architecture.svg)

The baseline is never edited where it sits: it is imported into a new GPO beside the Microsoft backup,
Halden deviations live in a separate higher-precedence GPO, and both go to a pilot OU before the fleet.
The one rule that keeps the hardening honest is enforced by the script rather than by memory:

```powershell
if (-not $ReviewedAuditDays -ge 7 -and -not $Force) {
    throw 'ASR rules must be audited for at least 7 days before blocking. Pass -ReviewedAuditDays <n>, or -Force with a recorded reason.'
}
```

The BitLocker phase has the same pattern with `-EscrowPolicyVerified`, because enabling encryption before
the key-escrow policy exists leaves a recovery key in nobody's hands. A control that only exists in a
runbook gets skipped at 18:00 on a Friday; one that exists in code does not.

## Results

**Not measured yet.** The build kit — scripts, configs, documentation and business artefacts — is
complete and the lab execution is pending. I am deliberately not publishing endpoint numbers before
they exist: the compliance percentage, the ASR event counts, the BitLocker coverage and the restored
key all become real values once the phases run, each with a file in `evidence/public/` as its source.

One set of figures does exist today, and it is **synthetic**: a 150-device invented fleet, generated
deterministically by a script in this repository, classifies as **78 ready, 41 upgrade, 31 replace**,
with a Windows 10 population of 72 devices (48%). Those counts are plain arithmetic over the generated
CSV — reproducible by re-running the generator with the same seed — and they describe **no real
hardware**. They exist because the lab has two Windows 11 VMs and one Windows 10 VM: enough to prove the
procedure, nowhere near enough to talk about a fleet. Every place the figure appears it says
"synthetic fleet", including the management report, because a planning number that looks like a survey
is worse than no number at all. The *rules* it is measured against — TPM 2.0, Secure Boot, UEFI, a
supported CPU, 4 GB RAM, 64 GB disk — and the code that applies them to real machines are real.

## Business side

The technical work is half of an endpoint project; the other half is what the business approves and
receives:

- **A one-page executive brief** — the situation, why it matters commercially, what will be enforced,
  what it costs, and four decisions the reader is being asked to take. Written for somebody with five
  minutes.
- **An endpoint security standard** that a manager can actually approve: each requirement states what
  is enforced, why it exists and what a user will notice — including an explicit list of what is
  deliberately *not* required (USBs are not blocked, no BitLocker PIN by default), because unexplained
  exclusions are what auditors write up.
- **A Windows 11 readiness report** with a costed three-option recommendation (upgrade and replace;
  upgrade with Extended Security Updates as a bridge; do nothing) and the risks of each, based on a
  clearly labelled synthetic fleet with a note on which departments hold the oldest devices.
- **An ASR exception register**, deliberately empty until the audit run fills it, so that the first row
  is evidence rather than a guess.
- **A change record** in the company's change format, with the risk, the test plan and the backout for
  every control, feeding the P10 governance dashboard.
- **A staff communication** explaining what changes, what users will actually notice, and how to request
  software — because "you no longer have admin rights" without a route to a fix is how a good control
  gets a bad reputation.

## What I learned / what I'd do differently

- **Put the sequencing in code, not in the runbook.** "Audit first" and "escrow before you encrypt" are
  exactly the instructions that get skipped under time pressure. Making the script refuse without a
  confirmation flag turned two good intentions into two controls.
- **The honest compliance figure is the less flattering one.** My first version of the report counted
  checks it could not measure as passes, which quietly inflated the score. Amber "not checked",
  excluded from the percentage, is both more accurate and more useful to a manager.
- **Be blunt and repetitive about synthetic data.** The fleet analysis is only meaningful if the reader
  knows instantly that it describes an invented estate; anything that looks like a measurement but is a
  plan is a trust problem waiting to happen.
- **I would move tamper protection into scope next time.** It is the one control an endpoint standard
  leans on that cannot be fully centralised without Intune or Defender for Endpoint, so in this lab it
  is set manually and recorded as a gap rather than claimed as covered.
